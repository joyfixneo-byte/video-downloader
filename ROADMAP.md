## ✅ Сделано

### Скачивание (ядро)
- yt-dlp + ffmpeg, бэкенд FastAPI, фронтенд — один `backend/static/index.html`.
- Плейлисты → выбор серий галочками; качество (лучшее/1080/720/480/mp3).
- Прогресс в реальном времени; мини-игра «Тетрис» как экран загрузки.
- Автоудаление файлов через 3 часа; размер файла; список файлов на сервере.
- Остановка и удаление задач; необязательный пароль на вход.
- Фикс тяжёлых видео: список «на сервере» и выдача `/api/file` теперь читают
  готовый файл с диска и **игнорируют недокачанные** (`.part`/фрагменты), а
  активные задачи скрыты из списка — размер больше не «прыгает», файл не
  скачивается битым («чёрный экран с кодом»), и его можно забрать даже после
  перезапуска сервиса (`vdup`). Ссылки на файл — с атрибутом `download`.

### Транскрибация видео в текст
- Сначала готовые субтитры через yt-dlp (мгновенно, **оригинальный язык** —
  приоритет `info["language"]`, затем ru/en/любой), одним запросом.
- Если субтитров нет — локальный **Whisper** (faster-whisper, CPU, бесплатно).
- Лёгкий аудио-формат (`bestaudio/worstaudio/worst`) — не качаем весь видеофайл.
- Два режима Whisper: **быстрый** (`base`, `beam_size=1`) и **точный**
  (`WHISPER_MODEL_ACCURATE`, по умолч. `small`, `beam_size=5` +
  `condition_on_previous_text` + мягкий VAD) — точнее на русском/плохом звуке.
- **Субтитры с таймкодами**: и готовые (парсинг VTT в сегменты `start/end/text`,
  схлопывание дублей авто-субтитров), и Whisper возвращают сегменты со временем.
- Кнопка **«🎙 Свои субтитры»** — распознать своей моделью (точный режим),
  игнорируя встроенные авто-субтитры (`force_whisper`); из готовой задачи со
  встроенными есть кнопка «Сделать свои субтитры».
- **Скачивание в файл**: `.srt` (с таймкодами) и `.txt` (сплошной текст),
  генерируются на фронте из сегментов (Blob, BOM); переключатель показа таймкодов.
- Понятный статус по стадиям («Скачиваю аудио…» → «Загружаю модель…» →
  «Распознаю NN%») + счётчик времени; кнопка «Остановить». Кнопка «Копировать».

### Безопасность (перед выводом в интернет)
- **Пароль `DOWNLOADER_PASSWORD`** — основная защита (включён на проде).
- SSRF-guard: только http/https на публичные адреса (блок localhost, приватных
  сетей, облачных метаданных) на `/info`, `/download`, `/transcribe`.
- Потолок одновременных задач (`JOB_CEILING`/`TJOB_CEILING`) → 429 при флуде.
- Whisper сериализован семафором (`MAX_ACTIVE_TRANSCRIBE`), лимит длины ролика
  (`WHISPER_MAX_MINUTES`); необязательный лимит размера файла (`DOWNLOAD_MAX_GB`).

### Интерфейс
- Редизайн в стиле клейморфизм: приглушённый градиент (teal→персик),
  коралловый акцент, маджента-свечение на фокусе, шрифты Space Grotesk + Inter.
- Фикс автозума на iPhone Safari: поля ввода ≥16px + `maximum-scale=1`
  (страница больше не зумится и не «ездит» при тапе на поле ссылки).
- **Зум полностью отключён**: `user-scalable=no` + `touch-action:manipulation`
  + ручное глушение пинча и двойного тапа JS (iOS игнорит user-scalable) —
  случайный промах по кнопке в тетрисе больше не зумит и не ломает игру.
- Тетрис: рекорд хранится в localStorage; превью следующей фигуры;
  кнопки «Заново» и «Пауза» рядом (не нажать случайно при игре).
  Игра доступна **всегда** (отдельная карточка), а не только при загрузке;
  пауза с оверлеем «ПАУЗА», возобновление, клавиша P.

### Инфраструктура / деплой
- Работает на **VM-apps-vpn** (egress через VPN → YouTube доступен).
- Виден в интернете: `http://91.186.220.103:8000`
  (Интернет → VPS nginx :8000 → frps → frp-туннель → VM-apps-vpn :8000).
- Обновление одной командой: **`vdup`** (алиас → `deploy/update.sh`).
  Делает `git pull` с HTTP/1.1, автоповтором и таймаутом (VPN то рвёт, то
  подвешивает соединение с GitHub) и перезапускает сервис только если менялось
  что-то кроме `backend/static/`. `vdup --no-restart` — только pull.

## 🚧 Торренты — Фаза 1: поиск + скачивание ✅ (код готов, нужна проверка на VM)

Цель фазы: нашёл раздачу (или вставил magnet) → **aria2 качает её на сервер**,
файл появляется в общем списке и отдаётся теми же ручками, что и yt-dlp-загрузки.
Просмотр — после докачки (стриминг во время загрузки — Фаза 2 ниже).

Сделано в коде (`backend/app.py` + `static/index.html`):
- **Движок:** `aria2c` как subprocess в `DOWNLOAD_DIR/<job_id>/`, `--seed-time=0`
  (не раздаёт после докачки). Прогресс парсится в те же поля `JOBS`
  (percent/speed/eta/total), поэтому фронтовый `poll()`, `/api/status`,
  `/api/files`, `/api/file`, `/api/cancel`, `/api/delete` и автоочистка
  работают для торрентов **без изменений** (переиспользование, не дубли).
- **Поиск:** скрейпер 1337x на stdlib (`GET /api/torrent/search?q=`), magnet
  берётся лениво при добавлении. Ручной ввод magnet — запасной путь.
- **Добавление:** `POST /api/torrent {magnet|detail}`, валидация magnet-схемы,
  тот же потолок задач `JOB_CEILING`/429.
- **UI:** карточка «🧲 Торренты» (поиск + вставка magnet), результаты с
  сидами/размером, кнопка «Скачать» кладёт задачу в общий список загрузок.

⚠️ **Требуется ручная проверка на VM (human-in-the-loop):**
1. Поставить движок: **`apt install aria2`** на VM-apps-vpn.
2. Проверить, что **поиск реально что-то находит** через VPN (1337x может быть
   за Cloudflare / сменить вёрстку → тогда 502, вставляем magnet вручную;
   зеркало меняется через env `TRACKER_BASE`).
3. Проверить **связность aria2 через VPN** на легальной раздаче (Ubuntu ISO):
   пиры/DHT/трекеры должны быть доступны через туннель, файл докачивается.
4. Нет жёсткого лимита размера торрента (у yt-dlp есть `DOWNLOAD_MAX_GB`) —
   следить за диском; лимит — в бэклоге.

### Дополнение: выбор файлов + без автоудаления ✅ (код готов, нужна проверка на VM)

- **Автоочистка:** папка торрент-задачи помечается файлом `.torrent_job` —
  `_cleanup_loop` такие папки больше не трогает вообще, удаление только
  вручную кнопкой «Удалить». Маркер на диске (не в `JOBS`), переживает
  рестарт сервиса.
- **Выбор файлов до скачивания:** `POST /api/torrent/files {magnet|detail}` —
  aria2 качает только метаданные (`--bt-metadata-only`, секунды), свой
  мини-декодер bencode (без новой зависимости) достаёт список файлов
  (имя/размер), фронт показывает чекбоксы (переиспользован паттерн выбора
  серий плейлиста). `POST /api/torrent {token, files}` качает выбранное
  через `--select-file`. Если метаданные не получить (нет пиров) — запасной
  путь «Скачать всё как есть» (старое поведение, без выбора).
- **Просмотр скачанных файлов:** `GET /api/torrent/{job_id}/files` сканирует
  папку задачи с диска (переживает рестарт), фронт рисует раскрывающуюся
  табличку (имя/размер/ссылка) через нативный `<details>`; `/api/file`
  принимает `?path=` для скачивания конкретного файла раздачи.

⚠️ **Требуется ручная проверка на VM:** реальный `--bt-metadata-only` фетч
метаданных и `--select-file` через VPN/живые пиры — здесь не воспроизвести,
только модульно протестировано (bencode-парсинг, HTTP-эндпоинты с
подменённым aria2, path traversal, автоочистка) без сети.

## 🚧 Фаза 2 — просмотр видео во время загрузки (стриминг)

Цель: **смотришь видео в браузере, пока оно качается**.
1. **Sequential download** — aria2 для BT его толком не умеет; вероятно нужен
   `libtorrent` (python-биндинги) с последовательным режимом.
2. **Стриминг в браузер:** отдача файла с HTTP Range, плеер `<video>` (играет по
   мере докачки первых кусков).
3. **Кодеки:** mp4/H.264 играет нативно; для mkv — опционально ремукс через ffmpeg.
4. **Сеть/безопасность:** уже под тем же паролем; юридическая оговорка (в UI есть).

### DEV-1. Telegram-бот для загрузки YouTube в SMB

**Статус:** реализовано локально; unit/journal/backend-проверки прошли. Перед production остаются настройка токена и проверка Telegram/YouTube/SMB на VM.

- **Цель:** отправить боту ссылку YouTube и получить видео в SMB-медиатеке,
  не проходя вручную сайт и кнопку «В библиотеку».
- **Что изучить/спроектировать:** интеграцию с существующим yt-dlp-потоком
  (`/api/download`, `_run_download`) и SMB-публикацией (`_publish_to_share`);
  способ запуска фонового Telegram-бота, сохранение токена и разрешение
  доступа только нужным отправителям; сообщения о результате и ошибках.
- **Подзадачи:** выбрать модель доступа и управления задачами; определить,
  скачивать ли напрямую в SMB или использовать текущую временную папку;
  описать обработку повторных ссылок, плейлистов и ошибок сети/SMB; определить
  настройку секрета и запуск сервиса на VM.
- **Сложность:** средняя.
- **Зависимости:** DEV-2 — решение о целевом хранилище и общем потоке публикации.
- **Риски:** утечка токена или открытый доступ к дорогим загрузкам; потеря
  задачи при недоступной SMB-шаре; отдельный процесс должен переживать рестарт.
- **Ожидаемый результат:** утверждённая спецификация приватного Telegram-бота,
  сценариев ответов, конфигурации/развёртывания и ручной проверки на VM.
- **Ответы интервью:** только один заранее настроенный Telegram ID; сразу
  в SMB; лучший доступный вариант качества; сообщать итог обработки и дать
  кнопку остановки; если видео уже есть, не скачивать повторно.

#### Implementation Spec — DEV-1 (утверждена)

1. **Цель.** Личный Telegram-бот принимает YouTube-ссылку, скачивает лучший
   доступный видео- и аудиопоток и сохраняет готовый файл в SMB-медиатеке.
   Бот сообщает об успехе/ошибке, позволяет остановить задачу и не запускает
   повторную загрузку того же видео.
2. **Компоненты.** Новый фоновый worker, например `backend/telegram_bot.py`,
   отдельная настройка `TELEGRAM_BOT_TOKEN` и разрешённого Telegram ID;
   общий слой задач/загрузки в `backend/app.py`; SMB-каталог и временные
   незавершённые файлы; systemd unit/deploy-инструкция для worker; журнал
   `docs/FUNCTIONS.md` после реализации.
3. **Сценарий.** Worker проверяет отправителя и домен/тип ссылки → получает
   метаданные YouTube и canonical video ID → ищет уже выполняющуюся или
   сохранённую загрузку → при дубле отвечает, где файл находится, и не
   скачивает его → иначе создаёт задачу с `bestvideo+bestaudio/best` → пишет
   временный файл в целевую SMB-файловую систему и публикует его только после
   завершения/склейки → присылает итог → inline-кнопка «Остановить» вызывает
   общий механизм отмены и удаляет только неполный временный файл.
4. **Решения.** Доступ только по одному заранее настроенному Telegram ID;
   Telegram Bot API используется через long polling, чтобы не открывать
   входящий webhook-порт; качество всегда лучшее доступное; для дублей
   постоянный индекс хранит canonical ID и имя файла, а старые файлы без
   индекса сверяются по нормализованному имени как legacy fallback. Worker
   запускается только на инстансе с YouTube-доступом через VPN; конфигурация
   самого приложения остаётся общей для обеих VM. Повторные загрузки — нет.
5. **Человек проверяет.** Перед запуском предоставить токен и Telegram ID
   через защищённые настройки VM; на VM проверить приём сообщения только от
   разрешённого аккаунта, лучший поток, остановку, повтор URL, ошибочную/не
   YouTube-ссылку и наличие готового файла в SMB/на ТВ.
6. **План проверки.** Модульные проверки allowlist, canonical-ID-дедупликации,
   состояний worker и отмены; интеграционная проверка yt-dlp → SMB на живом
   YouTube-видео; повторная проверка после перезапуска worker; синхронизировать
   `docs/FUNCTIONS.md` и выполнить `python backend/test_functions_journal.py`.

**Оценка:** средняя/высокая. **Зависимость:** согласовать DEV-2. **Риск:**
legacy-файл без source ID может совпасть по имени с другим роликом; при такой
неоднозначности бот должен сообщить о возможном дубле, а не молча перезаписать.




**Implementation outcome (2026-10-14):** Added `backend/telegram_bot.py` using stdlib long polling and SQLite, plus a systemd unit installed but enabled manually only on apps-vpn. ### DEV-2. Единая модель разделов «На сервере» и «Библиотека SMB»

**Статус:** реализовано локально; unit/journal/backend-проверки прошли. Перед production остаётся ручная проверка на VM.

- **Цель:** решить, нужны ли пользователю обе карточки и можно ли устранить
  лишнее копирование, сохранив понятный статус и надёжность хранения.
- **Что изучить/спроектировать:** различия между временной `DOWNLOAD_DIR`
  (автоочистка) и постоянной SMB-витриной; потоки обычных видео и торрентов;
  текущую публикацию файлов и поведение при недоступной SMB-шаре. Повторно
  использовать существующие API и `_publish_to_share`, не проектировать
  вторую систему хранения без необходимости.
- **Подзадачи:** описать реальные сценарии двух карточек; сравнить единый
  список с сохранением двух хранилищ и прямую загрузку в SMB с временной
  загрузкой/публикацией; предложить целевую модель и безопасный переход;
  определить, как показывать недоступность SMB и уже существующие файлы.
- **Сложность:** средняя/высокая.
- **Зависимости:** исходный архитектурный этап; решение влияет на DEV-1 и DEV-3.
- **Риски:** незаметная потеря временной/постоянной копии, неполная запись на
  SMB и изменение поведения очистки.
- **Ожидаемый результат:** рекомендация с аргументами и границами миграции,
  затем отдельная implementation spec с критериями целостности файлов.
- **Ответы интервью:** один общий список; обычные загрузки сразу в SMB;
  SMB — смонтированное хранилище на этом же сервере, отдельный сценарий
  «сервер доступен, а SMB недоступен» не проектируем. Ошибки файловой системы
  (например, нет места/прав на запись) всё равно должны быть видны как ошибки.

#### Implementation Spec — DEV-2 (утверждена)

1. **Цель.** У пользователя остаётся одно место для файлов: единая библиотека
   SMB; приложение не показывает отдельный пользовательский список временных
   «Файлов на сервере» и не копирует готовое видео с локального диска в SMB.
2. **Компоненты.** `backend/app.py`: общий целевой путь/публикация, yt-dlp и
   aria2 output/staging, `/api/files`, `/api/library` и связанные статусы;
   `backend/static/index.html`: одна карточка/список и действия над задачами;
   `docs/FUNCTIONS.md` и `ROADMAP.md`. Существующие `_publish_to_share()`,
   `/api/library`, `/api/files`, `/api/status` и торрент-маркеры изучить и
   расширять/переиспользовать.
3. **Сценарий.** Задача загружается в скрытый staging-каталог на той же
   смонтированной файловой системе SMB → `.part`/незавершённые файлы не
   попадают в список медиатеки → после проверки завершённости и склейки файл
   атомарно переименовывается в медиатеку → единый список показывает файл и
   задачу; после завершения временные рабочие данные удаляются, torrent
   metadata сохраняются только если нужны для возобновления/докачки.
4. **Решения.** Целевой дом — SMB; «на сервере» перестаёт быть отдельным
   разделом. Не держать постоянную копию в `DOWNLOAD_DIR`. Для обычного
   yt-dlp использовать временный файл и финальный rename в рамках SMB mount;
   для aria2 проверить безопасную запись в staging на SMB, чтобы не публиковать
   недокачанные файлы. SMB и приложение находятся на одной VM, поэтому отдельный
   режим удалённой SMB-недоступности не нужен; ошибки записи/диска не маскировать.
   До фиксации поведения торрентов подтвердить, что текущие resume, sparse-file
   проверки, повторная проверка хэша и докачка работают с новым путём.
5. **Человек проверяет.** На VM проверить фактический mount path и атомарность
   rename; доступность файлов через ТВ/VLC; свободное место; рестарт во время
   загрузки и восстановление/удаление неполного staging. Утвердить решение о
   миграции уже лежащих в `DOWNLOAD_DIR` файлов (не переносить автоматически
   без проверки имени и целостности).
6. **План проверки.** Проверить загрузки одиночного видео, плейлиста, отмену,
   ошибку/заполнение диска, торренты с выбором файлов/докачкой и рестарт;
   убедиться, что в выдаче нет `.part`, нет двух готовых копий, а SMB-список
   переживает рестарт. Обновить журнал функций и выполнить проверку журнала.

**Оценка:** высокая. **Зависимость:** исходная архитектурная задача, затем DEV-1
и DEV-3. **Риск:** aria2 и текущие проверки готовности могут вести себя иначе
на SMB mount; безопасный staging и проверка файла обязательны.

**Итог реализации (14 октября 2026):** сайт показывает задачи и готовые SMB-файлы
в одной карточке «Библиотека SMB». Новые yt-dlp и aria2 загрузки используют
скрытый `SHARE_DIR/.staging`; готовые файлы атомарно переименовываются в корень
SMB, а торрент-метаданные остаются для resume и докачки. Старые файлы
`DOWNLOAD_DIR` остаются совместимыми и не переносятся автоматически. Добавлены
понятные ошибки для незаданной/непригодной SMB-папки и нехватки места.

Локально проверены компиляция `backend/app.py`, регрессии torrent/file API и
синхронность `docs/FUNCTIONS.md`. На VM вручную проверить mount и атомарность
rename, воспроизведение на ТВ/VLC, свободное место, рестарт во время загрузки,
resume и докачку торрента с выбором файлов.

### DEV-3. Удобный список файлов и стабильная вёрстка

**Статус:** реализовано локально; unit/JS syntax и browser smoke-проверки прошли. Перед production остаётся ручная проверка на длинной истории и реальном телефоне.

- **Цель:** сделать длинные списки проще для просмотра и управления; дать
  сортировку и сворачивание готовых файлов по задаче; убрать скачки страницы

- **Что изучить/спроектировать:** обе текущие карточки списков (`serverCard`,
  `libraryCard`), рендеринг `loadServerFiles()`, `loadLibrary()` и карточек
  загрузок через `poll()`. Переиспользовать уже существующее раскрытие файлов
  торрента и сортировку его таблицы там, где подходит.

  группировку по исходной задаче и сворачивание завершённых групп; выбрать
  колонки сортировки и устойчивый порядок; закрепить геометрию области ввода и
  загрузок, обновлять только изменившиеся части карточки; проверить длинные

- **Сложность:** средняя.
- **Зависимости:** DEV-2 определяет, какие списки и состояния останутся.
- **Риски:** потеря состояния свёрнутых групп при опросе; скачки высоты при

- **Ожидаемый результат:** утверждённая спецификация поведения списка,

#### Implementation Spec — DEV-3 (утверждена)

1. **Цель.** Пользователь быстро находит файлы в длинной истории, видит их
   связь с исходной задачей, сворачивает завершённые группы и сортирует список.
   Вставка/разбор ссылки и новые статусы не двигают элементы под пальцами.
2. **Компоненты.** Разметка и CSS в `backend/static/index.html`; функции
   `loadServerFiles()`, `loadLibrary()`, `startJobCard()`, `poll()` и текущая
   таблица файлов торрента; при необходимости агрегированный read-only endpoint
   в `backend/app.py`; затем запись новых точек входа в `docs/FUNCTIONS.md`.
3. **Сценарий.** Список рисуется группами по задаче; активные группы раскрыты,
   завершённые можно свернуть общей командой и индивидуально; внутри групп
   сортировка переключается по имени/дате/размеру/статусу; обновление прогресса
   меняет только статус/кнопки конкретной карточки, сохраняя сортировку,
   прокрутку и состояние сворачивания. Постоянная область ввода/действий
   доступна сбоку на широком экране; на мобильном открывает отдельную панель,
   не вставляя новые поля в поток длинного списка.
4. **Решения.** Сначала применять DEV-2: конечный список — единая библиотека
   и связанные с ней активные задачи, а не два параллельных списка. Группы
   сохраняют связь файлов/серий с родительской загрузкой; активные задачи не
   скрываются общей командой «свернуть завершённые». Сортировка работает без
   повторной загрузки и при обновлении не сбрасывает выбранное поле/направление.
   Переиспользовать сортировку и раскрытие таблиц торрентов, если паттерны
   подходят; не добавлять отдельный механизм только для торрентов.
5. **Человек проверяет.** На телефоне проверить панель ввода, прокрутку и
   кнопки во время активного опроса; на десктопе — длинный список, фокус
   клавиатуры и закрытие панели; подтвердить, что группировка по задаче
   совпадает с ожидаемым сценарием для плейлиста и многофайлового торрента.
6. **План проверки.** Проверить длинную историю с активными, завершёнными,
   отменёнными и ошибочными задачами; сортировку с одинаковыми значениями;
   сохранение scroll/collapse/sort при polling; появление и закрытие панели без
   скачка списка; проверить мобильную и широкую ширину в браузере. Сверить
   пользовательские подписи и затем обновить журнал функций.

**Оценка:** средняя. **Зависимость:** DEV-2. **Риск:** группировка теряет
   файлы после обновления статуса или ошибочно объединяет разные задачи;
   группировать по стабильному `job_id`, а не по отображаемому названию.

**Итог реализации (14 октября 2026):** Активные задачи и файлы показываются в
едином списке, сгруппированном по стабильным ID; выбранные элементы плейлиста
получают общий `groupId`, который сохраняется в браузере. Добавлены сортировка
по имени/дате/размеру/статусу, индивидуальное и общее сворачивание завершённых
групп с сохранением настроек, и закреплённая кнопка панели ввода/действий.
Панель открывается как modal, а polling обновляет только изменившиеся поля
