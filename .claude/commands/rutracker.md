# Rutracker-интеграция: бриф для продолжения

Это перенос контекста из предыдущей сессии. **Читай целиком, ничего не переспрашивай
про то, что уже здесь написано.** Задача ведётся по процессу `speckit`
(интервью → спецификация → утверждение → код). Шаг 1 (интервью) уже задан,
ждём ответы. Кода до утверждённой спецификации — нет.

Аргументы к команде: $ARGUMENTS

## Задача (формулировка пользователя, дословно)

> напиши по хорошему api спецификацию для внедрения для vm-apps-vpn, на vm-apps не
> будем это добавлять, продумай как сделать чтобы не разделать проект на две ветки и
> обновлять одинаково на обеих машинах, пусть проверяет например доступность сайта и
> показывает явно есть ли доступ, а так как без vpn не будет доступа к рутрекеру то и
> скрывать всё что ты добавишь, но пусть явно это пишет, не бери это как готовое
> решение, подумай хорошо, и предложи варианты

Разбор требований:

1. Rutracker-поиск работает **только на инстансе apps-vpn** (:8000, egress через VPN).
2. На инстансе apps (:8002, без VPN) — эта функциональность **скрыта**, но UI
   **явно сообщает**, что она есть и почему недоступна.
3. **Одна ветка `main`, один код на обеих машинах.** Никаких форков, никаких
   `if VM == ...` в коде — различие только в конфигурации/рантайме.
4. Приложение **само проверяет доступность** rutracker и явно показывает статус.
5. Нужны **варианты решения с обоснованием**, а не одно готовое.

## Что уже сделано: аудит библиотек (повторять не надо)

Проверены две готовые обёртки над rutracker.

### `nikityy/rutracker-api` (npm) — ОТКЛОНЕНА

- Логин уходит по **`http://`** — пароль в открытом виде на первом хопе.
  Хост захардкожен `this.host = "http://rutracker.org"`, изменить нечем.
- Мёртвая с 26.07.2020. Капчу не умеет. Парсер устарел.
- `axios@0.19.0` — CVE-2020-28168 (SSRF через редирект), CVE-2021-3749 (ReDoS),
  CVE-2023-45857.
- Node-рантайм в Python-проекте.
- Утечек/бэкдоров нет, но по совокупности — не брать.

### `py-rutracker-client` (PyPI, репо `GvozdevAD/py_rutracker`) — РЕКОМЕНДОВАНА

Версия 0.2.0 от 19.11.2025, MIT, автор Alexander Gvozdev, 10 звёзд / 3 форка.

Плюсы (проверено чтением исходников):

- **HTTPS везде** — весь `Url` enum на `https://rutracker.org`. `verify=False` нигде нет.
- Утечек нет: единственный хост во всём коде — `rutracker.org`, телеметрии нет,
  `eval`/`exec`/`pickle`/`subprocess` не используются.
- Пароль **не логируется** (рядом с авторизацией только
  `logger.debug("Начало процесса аутентификации")` / `logger.info("Аутентификация успешно выполнена")`),
  в исключения не попадает.
- Куки только в памяти (`requests.Session` / `aiohttp.ClientSession`), на диск не пишутся.
- `validate_auth_response()` отдельно **детектит капчу**.
- Живой проект, 0 issues, ~130 КБ тестов, sync + async клиенты.

Минусы / что учесть в спеке:

- **Path traversal**: `_prepare_download_path()` кладёт аргумент `filename` прямо в
  `Path()` без `os.path.basename()` и без фильтрации `../`. Имя **не** берётся из
  `Content-Disposition`, так что сервер навязать путь не может — опасно только если
  прокинуть в `filename` пользовательский ввод. **В спеке: никогда не передавать
  `filename` из веб-формы, либо `os.path.basename()` на своей стороне.**
- **Хост захардкожен** в enum — зеркала (`.net`, `.nl`) без патча не подставить.
  Для нас это скорее фича (подтверждает «только через VPN»), но зафиксировать надо.
- **Требует Python >= 3.13 строго.** Это блокер — см. вопрос 1.
- Тянет 6 зависимостей: `beautifulsoup4`, `aiohttp`, `requests`, `lxml`, `pydantic`,
  `tenacity`. CVE в этих минимумах нет, но вес заметный ради sync-клиента.
- Логгер по умолчанию пишет `Path.cwd() / "py_rutracker.log"`, уровень из
  `PY_RUTRACKER_LOG_LEVEL` (дефолт `WARNING`). Redaction'а нет — свои переменные
  в этот логгер не класть.
- Низкая популярность → **пинить версию** (`py-rutracker-client==0.2.0`), обновлять
  только с просмотром диффа.

Альтернатива, если Python < 3.13: свой минимальный клиент на `requests` + `BeautifulSoup`
(~40 строк: POST на `https://rutracker.org/forum/login.php`, куки в `Session`,
парсинг таблицы результатов `tracker.php`). Форма логина: `login_username`,
`login_password`, `login`.

## Контекст проекта (прочитано, повторно можно не изучать)

Деплой: два живых инстанса **одного и того же кода** из `main`, различаются только
инфраструктурой — `apps-vpn` (:8000, egress через VPN) и `apps` (:8002, прямой egress).
Пользователь обновляет обе машины вручную через `vdup`. См. `CLAUDE.md` и `ADDRESSES.md`.

Три опоры в существующем коде, на которые ляжет решение:

| Что | Где | Почему важно |
|---|---|---|
| `/api/config` отдаёт фронту `{password_required}` | `backend/app.py:1834` | готовая точка для «какие возможности есть на этом инстансе» |
| `.gated:not(.cond)` — карточки с классом `cond` не показываются при разблокировке, всплывают по условию | `backend/static/index.html:502` | готовый механизм «скрыть блок на apps» |
| `TRACKER_BASE` через env, systemd unit один на обе VM с закомментированными `Environment=` | `backend/app.py:999`, `deploy/video-downloader.service` | **прецедент «один код, разное поведение по env» уже есть → ветки не нужны ни в одном варианте** |

Ещё якоря:

- Вкладки Видео/Торренты: `showTab()` — `backend/static/index.html:491`,
  разметка вкладок — `:287`, карточка торрентов `#torrentCard` — `:347`.
- Текущий поиск торрентов (скрейпер 1337x на stdlib): `_search_torrents()` —
  `backend/app.py:1016`, ручка `GET /api/torrent/search` — `:1330`.
- Запуск закачки: `POST /api/torrent {magnet|detail}` — `backend/app.py:1548`,
  предпросмотр файлов раздачи `POST /api/torrent/files` — `:1493`.
- Движок — `aria2c` (`ARIA2_BIN`, `backend/app.py:997`), работает с magnet и с
  сохранённым `.meta.torrent`. Торрент-пайплайн переиспользует общие
  `/api/status`, `/api/files`, `/api/file`, `/api/cancel`, `/api/delete`.
- Зависимости: `backend/requirements.txt` (сейчас fastapi, uvicorn, yt-dlp, faster-whisper).
- Статус фичи в `ROADMAP.md` → раздел «Торренты — Фаза 1».

## Шаг 1 speckit: вопросы интервью (ждут ответа)

Если пользователь передал ответы в `$ARGUMENTS` или в сообщении — используй их и
переходи к спецификации. Если нет — **задай эти вопросы через `AskUserQuestion`,
вариантами под клик** (правило из `CLAUDE.md`, текстом в чат не спрашивать).
Максимум 4 вопроса за вызов: первый вызов — вопросы 1–4, второй — вопрос 5.
Варианты уже заготовлены ниже, бери как есть.

**Вопрос 1 — `Python на VM`. «Какой Python в venv на apps-vpn?»**
Блокер: `py-rutracker-client` требует строго `>=3.13`. Если ниже — пишем свой
минимальный клиент на `requests` + `BeautifulSoup`.

- `Не знаю — дам команду` (Рекомендую) — пользователь выполняет сам (память
  `ssh-access-policy`), одной строкой: `~/video-downloader/.venv/bin/python -V`
- `3.13 или новее` — берём готовую библиотеку, пин `py-rutracker-client==0.2.0`
- `3.12` — библиотека не поставится, свой клиент (~40 строк)
- `3.11 или старше` — то же, свой клиент

**Вопрос 2 — `Аккаунт`. «Под каким аккаунтом rutracker ищет сервер?»**
Поиск без логина не работает вообще.

- `Серверный аккаунт в env` (Рекомендую, если сайтом пользуешься только ты) —
  `Environment=RUTRACKER_LOGIN/PASSWORD` в unit-файле, как `DOWNLOADER_PASSWORD`.
  Риск: любой знающий пароль сайта ищет под твоим аккаунтом, а сайт в интернете
  по HTTP без TLS
- `Каждый вводит свои` — сервер креды не хранит, только сессионная кука в памяти
  процесса. Безопаснее, но логиниться придётся после каждого рестарта
- `Серверный + второй пароль` — аккаунт в env, но rutracker-раздел закрыт
  отдельным паролем поверх общего
- `Аккаунта пока нет` — сначала регистрация, спека пишется под серверный вариант

**Вопрос 3 — `Проверка`. «Что считать „доступ есть“ и как часто проверять?»**
«Сайт отвечает» и «логин прошёл» — разные вещи (капча). VPN на apps-vpn
периодически рвётся — видно по ретраям в `deploy/update.sh`, статус не вечен.

- `Полная, на старте + кнопка` (Рекомендую) — логин и пробный поиск при запуске,
  результат кешируется, в UI кнопка «Проверить снова». Честный статус, но
  медленнее старт
- `Дешёвый пинг раз в N минут` — фоновая проба соединения, без логина. Быстро,
  но не ловит «сайт открылся, а логин упал»
- `Ленивая — по факту ошибки` — ничего заранее не проверяем, показываем реальную
  ошибку в момент поиска. Меньше всего кода, статус в UI появляется не сразу
- `Полная + перепроверка по таймеру` — как первый вариант, плюс фоновое
  обновление статуса (поймает обрыв VPN на живом инстансе)

**Вопрос 4 — `Место в UI`. «Как rutracker соседствует с поиском 1337x?»**
Сейчас во вкладке «Торренты» один источник — 1337x, работает на обеих машинах.
Во всех вариантах 1337x на apps остаётся как есть, вкладка не пустеет.

- `Селектор источника` (Рекомендую) — в той же карточке переключатель
  1337x / rutracker; на apps в списке просто нет rutracker. Минимальный диф
- `Отдельная карточка` — своя карточка «Rutracker», целиком скрывается на apps
  через существующий `.cond`. Нагляднее, но дублирует разметку поиска
- `Rutracker основной` — на apps-vpn он по умолчанию, 1337x уходит в запасные

**Вопрос 5 — `Плашка`. «Как выглядит „скрыто, но явно сказано“ на apps?»**

- `Плашка со ссылкой на :8000` (Рекомендую) — на месте скрытого блока строка
  «Rutracker недоступен без VPN — открой этот же сайт на :8000» со ссылкой на
  второй инстанс из `ADDRESSES.md`. Скрыто и объяснено, и сразу понятно куда идти
- `Неактивная вкладка с тултипом` — элемент виден, но выключен, причина в подсказке
- `Только блок статуса инстанса` — отдельная строка «Этот сервер: без VPN.
  Доступно: … Недоступно: Rutracker», сам блок поиска молча отсутствует
- `Плашка + статус на обоих` — то же, что первый вариант, но и на apps-vpn явно
  пишем «Rutracker: доступ есть»

## Шаг 2 speckit: что писать после ответов

Спецификацию по структуре speckit: цель → файлы/компоненты → сценарий по шагам →
ключевые решения → зоны human-in-the-loop → план проверки.

Пользователь просил **варианты, а не готовое решение** — минимум по механизму
«одна ветка, разное поведение». Направления, которые надо сравнить (не как готовый
ответ, а как заготовка для анализа):

- **A. Явный env-флаг** (`RUTRACKER_ENABLED=1` в unit-файле только на apps-vpn) —
  предсказуемо, ноль сетевых проверок при старте, но конфиг машин расходится вручную.
- **B. Автодетект** — оба инстанса гоняют одинаковый unit, доступность определяется
  пробой соединения; сама сеть решает, где фича включена. Ноль ручной конфигурации,
  но статус может «мигать» при обрыве VPN.
- **C. Гибрид** — env-флаг как «разрешено вообще», автодетект как «сейчас реально
  доступно»; UI различает «выключено на этом сервере» и «включено, но сеть отвалилась».

Общее для всех: расширение `/api/config` до карты возможностей инстанса и
фронт, который скрывает/показывает блок через уже существующий `.cond`.

Обязательно учесть: кеш результата проверки (не долбить rutracker на каждый рендер),
таймаут пробы (не вешать `/api/config`), поведение при обрыве VPN на живом инстансе,
`os.path.basename()` на `filename`, пин версии библиотеки, отдельная запись в
`ROADMAP.md` и `requirements.txt`.

## Правила работы по этой задаче

- **Кода до утверждения спецификации нет.** Сначала спека → явное «ок» от пользователя.
- **Вопросы — только через `AskUserQuestion`, вариантами под клик** (`CLAUDE.md`).
- **Журнал функций обязателен** (`CLAUDE.md` → «Журнал функций»): каждая новая ручка
  идёт строкой в `docs/FUNCTIONS.md` в том же коммите, что и код, с заполненной
  колонкой «Где в интерфейсе»; перед коммитом зелёный
  `python backend/test_functions_journal.py`. Ручка без кнопки — незакрытая задача.
- Ponytail-режим активен: минимальный работающий диф, переиспользовать существующие
  механизмы (`/api/config`, `.cond`, общий торрент-пайплайн), не плодить абстракции.
- Команды на VM — писать пользователю одной строкой с подставленными путями,
  самому по SSH не ходить (память `ssh-access-policy`, `vm-command-style`).
- После готового кода — коммит и пуш в `origin/main` без переспрашивания
  (`CLAUDE.md`), но **только свои файлы**: в рабочей копии есть посторонние
  незакоммиченные изменения (`ROADMAP.md`, скриншоты в `docs/`) — не подмешивать.
- Деплой на обе VM пользователь делает сам (`vdup`), не автоматизировать.
