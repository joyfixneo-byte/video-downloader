# Спецификация: поиск по Rutracker только на инстансе с VPN

Статус: **черновик, ждёт утверждения**. Кода до «ок» нет.
Процесс — speckit, шаг 2 (спецификация после интервью).

## 1. Цель

Добавить поиск раздач по rutracker.org во вкладку «Торренты». Rutracker
доступен только с egress через VPN, то есть фактически только на инстансе
**apps-vpn** (:8000). На инстансе **apps** (:8002, прямой egress) блок поиска
по rutracker **не показывается**, но на его месте стоит явная плашка: функция
есть, здесь недоступна, вот ссылка туда, где работает.

Код — один и тот же в `main` на обеих машинах. Ни веток, ни форков, ни
`if VM == ...`.

## 2. Ответы интервью (зафиксировано)

| Вопрос | Ответ |
|---|---|
| Клиент rutracker | решено в §5.1 — свой на stdlib, версия Python не блокирует |
| Аккаунт | серверный, логин/пароль в `Environment=` unit-файла apps-vpn |
| Что решает видимость | **автопроба сети**: сервер сам стучится на rutracker |
| Место в UI | **отдельная карточка** «Rutracker» во вкладке «Торренты» |
| Что видно на apps | **плашка** «недоступно без VPN» со ссылкой на :8000 |

## 3. Варианты «один код — разное поведение» и почему выбран этот

| | A. env-флаг | **B. автопроба (выбран)** | C. гибрид |
|---|---|---|---|
| Что включает фичу | `RUTRACKER_ENABLED=1` в unit только на apps-vpn | успешный коннект к rutracker | флаг = «разрешено», проба = «сейчас работает» |
| Ручная настройка машин | расходится (два разных unit) | **нет, unit одинаковый** | расходится |
| Обрыв VPN на apps-vpn | не замечен, поиск молча падает | **карточка исчезает сама** | различает «сервер без VPN» и «VPN отвалился» |
| Сеть при старте | не трогаем | одна проба раз в 10 мин | одна проба раз в 10 мин |
| Цена | 1 строка | ~25 строк | ~30 строк + флаг |

Выбран **B**. Он буквально отвечает на постановку задачи: проверка нужна не
как «мониторинг сайта», а как единственный источник правды о том, показывать
ли карточку на этой машине. Плата за это — известная и принятая: если VPN
отвалится на apps-vpn, карточка пропадёт до восстановления (а не покажет
сломанный поиск). Плашка при этом объяснит причину.

Апгрейд до C — одна константа, если окажется, что мигание раздражает.

## 5. Ключевые решения

### 5.1. Свой клиент на stdlib, а не библиотека

`py-rutracker-client` отклонён, хотя аудит её оправдал. Причины:

- В проекте **сейчас 3 рантайм-зависимости** (`fastapi`, `uvicorn`, `yt-dlp`,
  плюс `faster-whisper`). Существующий скрейпер 1337x (`_tracker_get`,
  `_search_torrents`, `backend/app.py:1038`) написан на `urllib.request` + `re`,
  без `requests` и без `beautifulsoup4`. Библиотека притащит 6 новых пакетов
  (`aiohttp`, `lxml`, `bs4`, `requests`, `tenacity`, `pydantic`) ради ~40 строк.
- Она требует **строго Python ≥ 3.13**. На VM почти наверняка не он.
- Нам нужны ровно две операции: залогиниться и распарсить таблицу результатов.
  Обе — прямой аналог того, что уже написано для 1337x.
- Её же дефекты (path traversal в `_prepare_download_path()`, захардкоженный
  хост, свой логгер в `cwd`) нам не нужно обходить, если её нет.

**Следствие: вопрос «какой Python на VM» перестаёт быть блокером.** Код будет
работать на 3.9+. Если всё же хочешь знать версию, на apps-vpn одной строкой:

```
~/video-downloader/.venv/bin/python -V
```

Что пишем (весь клиент, ~40 строк рядом с блоком 1337x):

- `_rt_opener()` — `urllib.request.build_opener(HTTPCookieProcessor(CookieJar))`,
  один на процесс, под `threading.Lock`. Логин ленивый: POST на
  `https://rutracker.org/forum/login.php` полями `login_username`,
  `login_password`, `login`. Кука `bb_session` живёт в памяти, на диск не
  пишется.
- `_rt_get(path)` — GET с браузерным User-Agent, **декодирование `cp1251`**
  (rutracker отдаёт windows-1251, не utf-8 — на этом ломается наивный порт
  кода от 1337x). Если ответ содержит форму логина — один раз перелогиниться
  и повторить.
- `_search_rutracker(q)` — GET `tracker.php?nm=<query>`, разбор строк таблицы
  регулярками: заголовок и `t=<id>`, размер, сиды, личи. Точную разметку сверяю
  с живой страницей при реализации; форма ответа — **та же**, что у
  `_search_torrents()`: `{title, detail, size, seeders, leechers}`.

Пароль нигде не логируется и не попадает в текст исключений (`except` вокруг
логина отдаёт свою фразу, а не `str(e)` от urllib).

### 5.2. `detail` — и весь пайплайн скачивания переиспользуется как есть

Ключ к минимальному дифу. У результатов поиска 1337x уже есть поле `detail` —
путь к странице раздачи, из которой `_resolve_magnet()` (`app.py:1078`) лениво
достаёт magnet в момент нажатия «Скачать». Rutracker-результаты кладут в
`detail` строку вида `/forum/viewtopic.php?t=<id>`, а `_resolve_magnet()`
получает один `if`:

```python
if detail.startswith("/forum/viewtopic.php"):
    page = _rt_get(detail)          # с сессионной кукой
else:
    ...существующий путь 1337x...
```

Дальше — **ноль изменений**: `_resolve_torrent_source()` → `POST /api/torrent/files`
(предпросмотр и выбор файлов) → `POST /api/torrent` → `_run_torrent()` → aria2 →
общие `/api/status`, `/api/files`, `/api/cancel`, `/api/delete`. Magnet со
страницы раздачи виден только залогиненным — наша сессия это и обеспечивает.

Про path traversal из аудита: имя файла нам никогда не приходит от rutracker —
имена берёт aria2 из метаданных раздачи, ровно как сейчас. Отдельного
`filename` в API не появляется, `os.path.basename()` применять не к чему.

### 5.3. Проба доступности и три состояния

```python
RT_TTL = 600          # 10 минут — как часто перепроверяем
RT_PROBE_TIMEOUT = 5  # секунд, чтобы /api/config никогда не залипал
```

`_rutracker_state()` возвращает одно из:

| Состояние | Когда | Что видит пользователь |
|---|---|---|
| `ok` | логин/пароль заданы **и** `https://rutracker.org/forum/index.php` ответил 200 | карточка поиска |
| `no_network` | креды есть, коннект не удался (таймаут, TLS, DNS) | плашка «нет доступа без VPN» + ссылка на :8000 |
| `no_account` | `RUTRACKER_LOGIN`/`PASSWORD` не заданы | плашка «аккаунт не настроен на этом сервере» |
| `checking` | процесс только поднялся, первая проба ещё идёт | строка «проверяю доступ к Rutracker…» |

Правила:

- Результат кешируется на `RT_TTL`. `/api/config` **читает только кеш и никогда
  не ждёт сеть**; если кеш протух, он отдаёт старое значение и запускает
  обновление в фоновом демон-потоке.
- Первая проба стартует при загрузке модуля (демон-поток), поэтому к моменту,
  когда человек открывает страницу, состояние обычно уже известно.
- HTTPS в пробе выбран намеренно: подменённая DNS-запись или страница-заглушка
  провайдера дадут ошибку TLS, а не ложный 200.
- Реальная ошибка поиска (капча, смена вёрстки, протухшая сессия) сбрасывает
  кеш в `no_network` — то есть неудача в бою тоже двигает статус, бесплатно.

### 5.4. Отдача статуса — в существующем `/api/config`

`/api/config` (`app.py:1868`) уже вызывается фронтом ровно один раз в `init()`
и уже отвечает на вопрос «что доступно на этом инстансе». Расширяем:

```python
return {"password_required": bool(ACCESS_PASSWORD),
        "rutracker": _rutracker_state()}   # "ok" | "no_network" | "no_account" | "checking"
```

Отдельной ручки статуса не заводим — меньше кода, меньше строк в журнале.
Осознанный компромисс: `/api/config` без пароля, то есть любой, кто откроет
сайт, узнает булеву «на этом сервере есть VPN». На фоне того, что весь сайт
работает по HTTP без TLS (`ADDRESSES.md`), это не ухудшает картину.

Сам поиск закрыт паролем как все остальные ручки (`Depends(check_password)`).

### 5.5. UI

Во вкладке «Торренты» (`index.html:345`), **под** существующей карточкой 1337x:

```html
<div class="card gated cond hidden" id="rutrackerCard">
  <label>Rutracker</label>
  … поле «Название раздачи…» + кнопка «Искать» + #rtHint + #rtResults …
</div>
<div class="card gated cond hidden" id="rutrackerOff">
  <label>Rutracker</label>
  <div class="hint">…текст причины… <a href="http://91.186.220.103:8000">открыть на :8000</a></div>
</div>
```

Оба блока — `gated cond`, то есть механизм из `unlockApp()`
(`index.html:502`) их сам не показывает; показывает их `applyRutracker(state)`
после чтения `/api/config`. Ровно один из двух видим всегда.

Тексты плашки (дословно, чтобы «явно сказано» было проверяемым):

- `no_network` — «Rutracker доступен только через VPN. Этот сервер работает
  напрямую, поэтому поиск по нему здесь скрыт. Тот же сайт с VPN: <ссылка>».
- `no_account` — «Rutracker: на этом сервере не задан аккаунт
  (`RUTRACKER_LOGIN`/`RUTRACKER_PASSWORD`), поиск скрыт».
- `checking` — «Проверяю доступ к Rutracker…», через 3 с фронт перечитывает
  `/api/config` один раз.

Поиск: `torrentSearch()` получает аргумент источника вместо трёх захардкоженных
`id`. Рендер результатов и обработчик «Скачать» (`addTorrent(r.detail, …)`) —
общие, потому что форма ответа у обоих источников одинаковая (§5.2).

Карточка 1337x на обеих машинах остаётся ровно как сейчас. Вкладка не пустеет
нигде.

## 6. Сценарий по шагам

**На apps-vpn:** открыл сайт → ввёл пароль → вкладка «Торренты» → под
карточкой 1337x есть карточка «Rutracker» → ввёл запрос → «Искать» → список
раздач (сиды/размер) → «Скачать» → тот же предпросмотр файлов, что у 1337x →
«Скачать выбранное» → задача в «Загрузках», дальше всё как обычно.

**На apps:** то же до вкладки «Торренты» → вместо карточки Rutracker плашка с
причиной и ссылкой на :8000 → карточка 1337x работает как работала.

**Если VPN на apps-vpn упал:** в течение 10 минут карточка сменится плашкой
`no_network`; поиск, запущенный в этот момент, вернёт ошибку текстом и сбросит
статус сразу.

## 7. Зоны human-in-the-loop

1. **Аккаунт rutracker** — логин/пароль даёшь ты, я их не вижу и в репозиторий
   они не попадают. Ставятся только в unit-файл на apps-vpn.
2. **Проверка разметки** — точные регулярки поиска я смогу сверить только с
   живой страницей; на машине без VPN это не проверить. Если парсер вернёт
   пусто на реальном запросе — присылаешь запрос и что показал сайт, правлю.
3. **Капча при логине** — если rutracker её покажет, автоматом не обходим:
   статус станет `no_network` с текстом про капчу. Разбираемся вручную.
4. **Деплой** — `git pull` + `systemctl restart` на обеих VM делаешь ты (`vdup`).

## 8. План проверки

Перед коммитом:

```
python backend/test_functions_journal.py
python backend/test_rutracker.py
```

`test_rutracker.py` — одна самопроверка на `assert`: скармливает парсеру
кусок HTML таблицы результатов (сохранённый образец, cp1251-строка) и
проверяет, что вышли title / detail / size / seeders. Без фреймворков и
фикстур, сеть не трогает — падает ровно тогда, когда сломан разбор.

На apps-vpn после `vdup`:

1. «Торренты» → карточка «Rutracker» видна.
2. Поиск заведомо существующей раздачи → непустой список.
3. «Скачать» → предпросмотр файлов открылся → одна маленькая раздача докачалась.

На apps после `vdup`:

4. «Торренты» → плашка с причиной и рабочей ссылкой на :8000, карточки поиска
   по rutracker нет.
5. Поиск 1337x работает как раньше.

## 10. Что сознательно не делаем

- Кнопки «Проверить снова» нет — статус сам обновляется раз в 10 минут и по
  факту ошибки поиска. Добавим, если руками захочется дёргать.
- Зеркала rutracker (`.net`, `.nl`) не подставляем — задача сформулирована как
  «работает через VPN», зеркала это размывают.
- Раздачу после докачки не сидируем (как и сейчас, `--seed-time=0`).
- Скачивание `.torrent` через `dl.php` не используем — magnet со страницы
  раздачи проходит через уже существующий пайплайн без единой правки.
